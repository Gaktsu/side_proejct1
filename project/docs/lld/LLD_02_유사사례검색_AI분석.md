# LLD 02 — 유사 품질사례 검색 및 AI 원인 분석

- 작성 기준: 2026-10-22 논의 내용, `LLD 2.txt`, 「유력 사례 조회 및 LLM을 통한 원인 분석」 흐름도
- 상태: **기본 설계 합의 / 일부 상세 구현 미정**
- 범위: 단일 QualityCase ID로 분석을 요청한 뒤 후보 검색·평가·LLM 분석 결과를 제공하는 흐름
- 비범위: 품질사례 등록/RESOLVED 인덱싱(LLD 01), 담당자의 최종 판정 저장(후속 LLD)

## 1. 목표 및 입력

- 입력: 분석 대상 `qualityCaseId`.
- 목표: 유효한 해결 사례를 찾아 관련성과 근거를 재평가하고, 담당자가 검토할 수 있는 원인 후보·추가 확인 사항·요약을 생성한다.
- 전체 검색과 AI 분석을 **하나의 비동기 Analysis 작업**으로 관리한다.
- 후보가 준비되면 **SSE로 먼저 전송**하고, 작업자는 후보를 검토하면서 LLM 결과를 기다릴 수 있다.
- 최초 접수 응답은 작업 접수 및 식별자 전달이고, 분석 완료 응답과 구분한다.

## 2. 구성 요소와 책임

| 구성 요소 | 책임 |
|---|---|
| Client | 분석 요청, SSE 수신, 후보 및 최종 결과 표시 |
| Spring Boot | 작업 상태·권한·흐름 조율, 저장/조회, SSE 이벤트 전송, 오류 분류 |
| MySQL | QualityCase·Analysis·AnalysisCandidate·결과 및 상태 저장 |
| Embedding | 분석 대상의 문제 현상 등 검색 텍스트를 질의 벡터로 변환 |
| Qdrant | 검색 가능한 RESOLVED 사례의 유사 벡터 Top-K 검색 |
| JEV 또는 Reranker | 검색 후보의 관련성 재평가, 채택/제외 판단과 근거 기록 |
| LLM (로컬) | 채택된 사례를 근거로 원인 후보·확인 사항·요약 생성 |

> JEV/Reranker의 세부 선택과 입력 형식은 아직 확정하지 않았다. 벡터 재비교만을 수행한다고 가정하지 않는다.

## 3. 정상 흐름 (기본 합의)

1. 클라이언트가 `qualityCaseId`로 분석 요청을 보낸다.
2. Spring이 입력·접근 권한·해당 QualityCase 존재 여부를 검증한다.
3. MySQL에 `Analysis` 작업 및 초기 상태를 저장하고 **작업 ID를 반환**한다.
4. 백그라운드 작업이 질의 텍스트를 구성하고 Embedding을 호출한다.
5. Qdrant에서 검색 가능한 해결 사례를 Top-K 후보로 조회한다.
6. 후보 ID로 MySQL 원본을 조회하고 **현재 RESOLVED 여부, 논리 삭제 여부, 인덱싱 버전·유효성**을 확인한다. 유효하지 않은 후보는 LLM 근거로 사용하지 않는다.
7. **조회된 후보 모두** `AnalysisCandidate`에 저장하고 Qdrant 순위·유사도·평가 상태를 기록한다.
8. JEV/Reranker가 후보를 재평가한다. 제외된 후보를 삭제하지 않고 **평가 점수·채택/제외·사유**를 저장한다.
9. 채택 후보가 준비되면 MySQL에 중간 결과와 작업 단계를 반영하고, SSE로 `candidates_ready` 이벤트를 전송한다.
10. LLM에 채택 사례의 유효한 원본 텍스트와 문제 내용을 제공해 분석한다.
11. 결과 형식과 참조 사례 ID의 유효성을 검증하고 MySQL에 저장한다.
12. Analysis를 `COMPLETED`로 변경하고 SSE로 `analysis_completed` 이벤트를 전송한다.

### 흐름 요약

```text
Client --분석 요청--> Spring --Analysis 생성--> MySQL
   <--작업 ID--            |
   --SSE 구독------------->|--비동기--> Embedding --> Qdrant Top-K
                            |                 |
                            +-- MySQL 원본 유효성 검증
                            +-- 모든 Candidate 기록 --> JEV/Reranker 평가·기록
   <--SSE: candidates_ready--+
                            +-- LLM 분석 --> 결과 검증 --> MySQL 저장
   <--SSE: analysis_completed+
```

## 4. 데이터 변경과 저장 정책

| 시점 | MySQL | Qdrant |
|---|---|---|
| 작업 접수 | Analysis 생성 및 상태 기록 | 변경 없음 |
| 질의 임베딩 | **검색용 질의 벡터는 원칙적으로 영속 저장하지 않음** | 변경 없음 |
| 후보 검색 직후 | 모든 후보를 AnalysisCandidate에 기록 | 읽기만 수행 |
| 재평가 완료 | Candidate 점수·채택 여부·제외 사유 업데이트 | 변경 없음 |
| 후보 공개 | 후보 준비 단계 기록 | 변경 없음 |
| LLM 성공 | 생성 내용·근거 및 Analysis 완료 상태 저장 | 변경 없음 |
| LLM 실패 | Analysis `FAILED` 및 오류 정보 기록, 후보 이력 유지 | 변경 없음 |

- `AnalysisCandidate`는 **채택되지 않은 후보도 삭제하지 않는다.**
- 검색용 질의 벡터를 저장하지 않겠다는 결정은, LLD 01의 **인덱싱/복구용 벡터 보존 정책**과 별개이다.
- Candidate가 평가 전인지, 채택인지, 제외인지, 평가 오류인지 식별 가능한 표현이 필요하다(필드 구조는 미정).

## 5. 검색 및 근거 정책

- 검색 대상은 **현재 RESOLVED 상태이면서 인덱싱이 완료되고 검색 가능**한 품질사례로 제한한다.
- Qdrant payload의 `searchable=false` 필터로 오래된·취소된·논리 삭제된 사례를 검색에서 제외하는 **정책을 채택**한다.
- 단, Qdrant 상태 변경이 실패하거나 지연될 수 있으므로 후보 사용 전 MySQL 원본 상태와 버전을 추가 검증한다.
- Qdrant 벡터는 검색 제외 시 즉시 삭제하지 않는다. 원본 데이터·복구 정보는 별도 보존 정책을 따른다.
- 초기 Top-K 범위는 **3~10개**로 설정한다. 검색 결과가 그보다 적으면 실제 반환 건수를 그대로 사용하며 억지로 채우지 않는다.
- 재평가 후 채택 후보가 **0개면 근거 부족/후보 없음**을 정상적인 검색 결과로 안내한다(시스템 장애와 구분).
- 채택 후보가 **1~2개면 LLM 분석은 진행하되 근거가 제한적일 수 있음을 표시**한다. 후보 건수만으로 신뢰도를 확정하지 않는다.
- 참조 근거는 실제 후보와 연결되어야 하며, 담당자 최종 판정과 LLM 제안은 구분한다.

## 6. 작업 상태와 SSE

- 확정: **분석 전체가 하나의 비동기 작업**, 후보 먼저 표시, LLM 실패 시 Analysis `FAILED`, 기존 후보 유지.
- 다음 상태는 **구현 제안**이며 DB enum으로 확정된 것은 아니다.

| 예시 단계 | 설명 | 사용자 표시 |
|---|---|---|
| PENDING | 작업 접수 | 접수 완료 |
| SEARCHING | 임베딩·Qdrant 검색 | 유사 사례 검색 중 |
| RERANKING | 후보 검증·평가 | 후보 평가 중 |
| CANDIDATES_READY | 후보 저장·SSE 전송 가능 | 유력 사례 우선 표시 |
| ANALYZING | LLM 처리 | AI 분석 중 |
| COMPLETED | 결과 저장 완료 | 최종 결과 표시 |
| FAILED | 복구 불가능 또는 재시도 소진 | 오류 안내, 저장된 후보 유지 |

- SSE 예시 이벤트명: `candidates_ready`, `analysis_completed`, `analysis_failed` (이벤트 스키마는 후속 API 상세 설계에서 결정).
- **SSE는 이벤트 전달 방식이지 작업 보존 수단이 아님.** 연결 해제 후에도 Analysis는 계속 처리되며 재연결 시 저장된 상태·후보·결과를 다시 조회할 수 있어야 한다.
- 재연결 시 마지막 이벤트 재전송 방식, 이벤트 ID, 중복 표시 방지는 **미정**.

## 7. 트랜잭션 경계

- Analysis 작업 생성·상태 기록은 짧은 MySQL 트랜잭션으로 처리한다.
- 모든 Candidate의 초기 저장과 평가 결과 반영은 필요한 원자성 범위를 정해 별도 DB 트랜잭션으로 처리한다.
- LLM 결과 저장과 완료 상태 반영의 일관성을 고려한다.
- **Embedding, Qdrant 조회, JEV/Reranker, LLM 호출을 MySQL 트랜잭션 내에서 오래 실행하지 않는다.**
- DB 쓰기 성공 여부가 불명확한 경우, 중복 Candidate/Analysis 생성을 방지할 식별자·제약 정책은 후속 상세 설계에서 확정한다.

## 8. 실패 흐름과 복구 원칙

| 실패 지점 | 합의한 기본 처리 | 미정·주의점 |
|---|---|---|
| Analysis INSERT 실패 | 접수 실패를 HTTP로 안내 | 커밋 성공·응답 유실 시 중복 방지 필요 |
| 검색 질의 Embedding 실패 | 재시도 가능한 경우 **질의 전체를 다시 임베딩** | 독립 문서 청크가 없는 한 내부 연산 중간 재개 불가 |
| Qdrant 조회 실패 | 복구 시 재검색(질의 재임베딩 포함 가능) | 질의 벡터 미저장 방침과 일치 |
| Qdrant 검색 완료 직후 종료 | 후보 미저장이면 재검색; 저장됐으면 재사용 고려 | 작업 단계 영속화 범위 확인 |
| JEV/Reranker 실행 도중 종료 | 저장된 Candidate와 MySQL 원본으로 재평가 | 평가 미완료와 '제외'를 구분 |
| 평가 결과 후보 0건 | **정상적인 근거 부족 결과**로 안내 | 실행 오류와 혼동하지 않음 |
| LLM 실패 | Analysis `FAILED`, 이미 저장한 후보 유지, SSE 오류 이벤트 | 사용자에게 후보는 계속 보이게 함 |
| SSE 연결 끊김 | 서버 작업은 계속 실행 | 재접속 후 상태/후보/결과 동기화 필요 |

- 기존 초안의 **'청크별 내부 임베딩 상태를 DB에 저장하고 이어서 계산'** 정책은 현 구조에서 채택하지 않는다. 검색용 질의 벡터도 영속 저장하지 않는다.
- 재시도 최대 5회는 앞선 대화의 잠정 정책이지만, 오류 분류·횟수 기준(최초 실행 포함 여부)·대기 간격은 미정이다.

## 9. 최종 상태 정의

- **정상 완료:** Analysis 완료 상태 및 AI 결과 보존, 모든 Candidate와 평가 이력 보존, Qdrant에는 쓰기 없음.
- **후보 없음:** 정상 검색의 근거 부족 결과로 기록. LLM 실행 여부와 최종 상태 표현은 테스트를 거쳐 확정.
- **LLM 실패:** Analysis FAILED, 후보 이력은 조회 가능.
- **검색/평가 단계 실패:** 오류와 마지막 처리 단계를 기록하고 재처리 정책을 적용. 요청 자체가 실패했는지 작업이 접수된 후 실패했는지 구분.

## 10. 미정 및 검증 항목

1. JEV와 Reranker의 최종 선택, 임계점수, 후보 입력 형식.
2. Analysis 및 Candidate 실제 상태 컬럼과 유일성 제약.
3. SSE 재접속/중복 이벤트와 구체적인 API 스키마.
4. 장시간 PROCESSING 상태의 작업 회수 및 재처리 실행 방식.
5. 유력 후보 0건일 때 LLM 미실행 여부와 최종 Analysis 상태.
6. 3초·15초 성능 목표와 5건 동시 요청, 16GB 자원 제약의 실측 검증(별도 성능 점검 문서 참조).

## 11. 원래 흐름도 수정 체크리스트

- [ ] 검색 전체를 **비동기 Analysis 작업 + 작업 ID 응답**으로 표현
- [ ] 검색용 벡터의 DB 저장/청크별 복구 단계 제거
- [ ] 모든 검색 후보를 AnalysisCandidate에 저장한 뒤 평가, **제외 시 삭제하지 않고 상태 기록**
- [ ] Candidate 원본/상태/버전 유효성 확인과 `searchable` 필터 표시
- [ ] 후보 준비 시 `SSE candidates_ready` 분기, 이후 LLM 실행
- [ ] 성공/실패 모두 저장 상태와 SSE 이벤트로 표시
- [ ] 평가 실패(기술 오류)와 0건(정상 결과) 구분
- [ ] DB 트랜잭션과 외부 모델 호출 영역 분리
