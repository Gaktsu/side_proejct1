# LLD 03 — AI 분석 결과 저장 및 담당자 최종 판단

- 작성 기준: `LLD 3.txt` 및 2026-10-26 검토·후속 결정
- 상태: **핵심 기능 설계 합의 / 상세 장애 복구·출력 형식 미정**
- 범위: LLD 02에서 생성된 Analysis의 LLM 결과 검증·저장, 담당자의 확정 원인과 조치 기록
- 범위 밖: 검색 후보 생성·JEV 평가(LLD 02), RESOLVED 인덱싱(LLD 01), 전체 장애 복구 정책(LLD 05)

> 표기: **[결정]** 대화에서 확정한 정책, **[제안]** 구체화 가능한 구현안, **[미정]** 아직 선택하지 않은 설계. 이 문서의 필드/상태 예시가 현재 DB에 이미 존재한다는 의미는 아니다.

## 1. 목표 및 입력

### AI 분석 결과 저장
- 입력: `analysisId`, 관련 `qualityCaseId`, 채택된 `AnalysisCandidate` 및 유효한 원본 사례, LLM 결과.
- 재처리 시 기존 `analysisId`로 같은 *분석 작업*을 식별한다. 같은 QualityCase의 새로운 분석 요청은 별도 Analysis일 수 있다.
- **[결정]** AI 결과에는 원인 후보, 원인을 확인할 **여러 가지 추가 확인 방법**, 분석 요약이 포함되어야 한다. 원인 후보만 제시하는 결과로 끝내지 않는다.

### 담당자 최종 판단
- 입력: 품질사례 ID, 확정 원인, 실제 해결 조치, 필요에 따라 검사·확인 결과.
- **[결정]** AI 후보 중 실제 원인이 없을 수 있으므로 담당자의 확정 원인을 후보 중 하나로 제한하지 않는다.
- **[결정]** 최종 원인·조치·해결 내용은 `QualityCase`에 저장한다. `InspectionResult`는 검사·추가 확인에 대한 기록이며, AI의 최종 판단 저장소가 아니다.

## 2. 사전 조건

### AI 결과 저장
1. 대상 Analysis가 존재하며 작업 진행 상태가 유효한가?
2. 참조된 Candidate의 원본 QualityCase가 유효하며, 해당 근거를 사용해도 되는가? (LLD 02의 RESOLVED·논리삭제·인덱싱 버전 검증과 연계)
3. LLM 결과가 필수 구조를 만족하며 참조 ID가 실제 후보를 가리키는가?
4. **[주의]** 유력 후보가 0개인 것은 시스템 오류와 다르다. 근거 없음 처리 정책은 LLD 02에 따른다.

### 담당자 최종 판단
1. QualityCase가 존재하고 논리 삭제되지 않았는가?
2. 작업자가 해결 처리 권한을 보유하는가?
3. 원인·조치 등 해결 처리에 필요한 데이터가 유효한가?
4. **[결정]** AI 분석 결과가 없거나 AI가 잘못 판단했더라도 담당자가 자체 근거로 최종 원인을 기록할 수 있는 방향을 우선한다.

## 3. 정상 흐름

### A. AI 분석 결과 저장
1. LLD 02의 검색·재평가 결과를 바탕으로 비동기 Analysis 작업이 LLM 분석을 수행한다.
2. LLM은 가능한 원인 후보, 원인 확인을 위한 여러 추가 점검 방법, 요약을 반환한다.
3. Spring은 결과 형식 및 후보 근거의 참조 무결성을 검증한다. 형식이 맞지 않으면 정상 완료로 처리하지 않는다.
4. **[결정]** MySQL 트랜잭션에서 해당 Analysis의 분석 결과를 저장하고 완료 상태를 반영한다.
5. 저장이 완료된 후 SSE로 최종 완료 이벤트를 전송한다. 이전에 전송한 유력 Candidate와 연결된다.
6. 권한 있는 사용자는 저장된 Analysis를 재조회할 수 있다.

### B. 담당자 최종 판단 및 해결 요청
1. 담당자는 AI 결과와 필요 시 InspectionResult를 검토하되 AI 후보를 그대로 확정할 의무는 없다.
2. 실제 확인한 원인과 상세 조치 내용을 입력하고 품질사례 해결 처리를 요청한다.
3. Spring은 권한·필수값·업무 상태를 검증한다.
4. MySQL에서 QualityCase의 확정 원인·조치·결과 및 `RESOLVED` 변경을 기록한다.
5. **[연계]** QualityCase 해결 처리와 인덱싱 PENDING 기록은 LLD 01에서 정한 것처럼 하나의 MySQL 트랜잭션으로 처리한다.
6. 인덱싱은 별도 비동기 흐름으로 진행하고, 사용자는 해결 완료와 검색 반영 대기를 구분하여 확인한다.

## 4. 데이터 변경과 엔티티 책임

| 저장 대상 | 데이터 | 원칙 |
|---|---|---|
| MySQL `Analysis` | AI 원인 후보, 추가 확인사항, 요약, 작업 상태 | AI 추정·이력 관리 |
| MySQL `AnalysisCandidate` | 검색 후보, 점수, 채택·제외 결과 | LLD 02에 따라 모든 후보 이력 보존 |
| MySQL `QualityCase` | 담당자가 확정한 실제 원인, 조치, 결과, 해결 상태 | 실제 업무 판단의 기준 |
| MySQL `InspectionResult` | 검사·추가 확인의 실행 결과 | AI 결과·최종 판단과 분리 |
| Qdrant | 이 단계 자체에는 직접 변경 없음 | RESOLVED 반영은 LLD 01에서 처리 |

- **[결정]** AI 결과와 담당자의 최종 판단은 서로 덮어쓰지 않는다.
- **[미정]** 구체적인 JSON 응답 스키마, 원인 후보의 세부 필드, 프롬프트 템플릿 및 모델 버전 메타데이터.

## 5. 트랜잭션 경계

- LLM 모델 호출은 MySQL 트랜잭션 밖에서 수행한다.
- LLM 응답을 검증한 뒤 **Analysis 결과 저장과 완료 상태 변경**은 하나의 짧은 MySQL 트랜잭션으로 처리하는 방향이다.
- 담당자의 QualityCase 해결 변경과 인덱싱 작업 기록의 트랜잭션 경계는 **LLD 01**을 따른다.
- SSE 전송은 DB COMMIT 이후로 둔다. SSE 전송 성공을 DB 저장 성공의 조건으로 삼지 않는다.

## 6. 실패 흐름 및 복구

| 상황 | 현재 처리 방향 | 추가 검토 |
|---|---|---|
| LLM 호출·추론 실패 | 재시도 가능한 경우 LLM 재실행, 최종 실패 시 Analysis `FAILED` 기록 및 SSE 오류 안내 | 상세 횟수·타임아웃은 LLD 05 |
| LLM 결과의 구조/근거 검증 실패 | 정상 결과로 저장하지 않음 | 수정 재요청 가능 여부 미정 |
| LLM 성공, MySQL 일시 장애, Spring은 살아 있음 | **메모리에 남은 결과로 DB 저장만 재시도** | 저장의 중복 방지 필요 |
| LLM 성공, Spring 종료로 메모리 결과 유실 | Analysis의 미완료 상태를 기반으로 LLM **재실행 가능** | 재시작 시 미완료 작업 탐지: LLD 05 |
| DB 결과 저장 성공, SSE 연결 종료 | DB의 결과는 유지, 클라이언트는 재조회 가능 | SSE 재연결·누락 이벤트 처리: LLD 05 |
| MySQL 장기 중단 | DB에 `FAILED`조차 쓸 수 없을 수 있음 | 서비스 복구 후 상태 정합성 점검 필요 |

- **[결정]** 엑셀 파일을 장애 복구용 임시 저장소로 사용하지 않는다.
- **[의도/검증 목표]** 재실행 시 핵심 원인 후보가 대체로 일관되기를 원한다. 다만 LLM의 동일 출력은 보장되지 않으며, 추후 반복 실행 비교로 검증한다.

## 7. 최종 상태

### 성공
- Analysis에 검증된 원인 후보·복수의 추가 확인사항·요약이 저장되고 `COMPLETED` 상태가 된다.
- 기존 Candidate의 평가 이력이 보존된다.
- 담당자가 해결 처리하면 최종 원인·조치가 QualityCase에 저장되며 인덱싱은 LLD 01의 상태 관리대로 별도 진행된다.

### 실패
- 미완료/실패 Analysis를 식별할 수 있고, 후보 기록이 이미 존재한다면 보존한다.
- 분석 결과의 DB 저장 성공 전에는 사용자에게 최종 완료로 확정해 안내하지 않는다.
- 복구 가능 오류는 기존 작업을 기준으로 재처리하고, 결과를 중복 생성하지 않도록 한다.

## 8. 미정 사항 및 다음 단계로 이관

1. AI 출력 JSON 스키마와 프롬프트, 근거 검증 기준.
2. 담당자 판단 기록에 필요한 필수 필드와 InspectionResult와의 상세 관계.
3. 실패 Analysis의 재처리·복구 실행 주체, 재시도 제한, 오래된 PROCESSING 회수(LLD 05).
4. SSE 재연결 후 후보·분석 결과 복원 방식(LLD 05/구현).
5. 동일 입력 반복 분석 결과의 일관성 평가 기준(성능·품질 테스트).

## 9. 기존 `LLD 3.txt` 대비 변경 기록

- Excel 임시 저장·FIFO 복원안 **폐기**, 메모리 내 DB 저장 재시도 / 결과 유실 시 LLM 재실행으로 정리.
- 결과 내용 규칙만 있던 정상 흐름에 검증·저장·SSE 완료 및 담당자 해결 요청 순서를 추가.
- 담당자 확정 판단은 **QualityCase**, 검사 결과는 **InspectionResult**로 구분.
- AI 추정과 사람의 최종 판단의 독립성을 명시.
