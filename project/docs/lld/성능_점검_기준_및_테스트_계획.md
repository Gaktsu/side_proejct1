# 성능 점검 기준 및 테스트 계획 — 품질사례 RAG 시스템

- 작성 기준: 2026-10-22까지의 FR/NFR, HLD, LLD 01·02 논의
- 상태: **측정 계획 초안 / 수치는 목표이며 검증 전**
- 목적: 실제 환경에서 검색, LLM, 메모리, 동시성의 병목과 목표 달성 가능성을 확인하기

## 1. 현 단계의 잠정 목표

| 항목 | 잠정 목표 | 정의·유의사항 |
|---|---|---|
| 유사 사례 검색 구간 | **p95 ≤ 3초** | 입력 질의 Embedding 시작 → Qdrant 검색 → 원본 검증·JEV/Reranker 평가 완료까지 |
| LLM 분석 구간 | **p95 ≤ 15초** | 평가 완료 후보를 이용한 LLM 요청 시작 → 결과 생성·검증까지 |
| 동시 요청 | **5건** | 비동기 요청 접수와 실제 동시 실행을 구분해서 측정 |
| 전체 메모리 | **16GB 이내** | Spring, MySQL, Qdrant, Embedding, 로컬 LLM, Docker·OS 포함 |
| 검색 반영 지연 | **정상 상황에서 10분 이내** | RESOLVED와 PENDING 기록 커밋 → 최신 벡터 검색 가능 상태까지; 별도 인덱싱 테스트 |

- **p95:** 측정한 요청 중 약 95%가 해당 시간 이내 끝나도록 하는 목표. 성공한 요청만 따로 표시하면 오류를 숨길 수 있으므로 성공률도 별도로 기록한다.
- 실제 3초와 15초는 **측정 후 재조정할 잠정 목표**다. 현 시점에서 달성 가능하다고 확정하지 않는다.
- 전체 사용자가 느끼는 시간에는 작업 접수, 큐 대기, DB 저장, SSE 전달 시간이 추가될 수 있다. 따라서 **종단 간 완료시간**도 별도로 측정한다.

## 2. 측정 구간 정의

```text
POST 분석 요청
  ├─ 접수/Analysis 저장 -------------------- t_accept
  └─ 대기열 체류 -------------------------- t_queue
       └─ 질의 Embedding ------------------ t_embed
       └─ Qdrant Top-K ------------------- t_qdrant
       └─ MySQL 후보 검증/조회 ------------ t_fetch
       └─ JEV/Reranker ------------------- t_rerank
       └─ Candidate DB 저장 -------------- t_candidate_db
          └─ SSE 후보 이벤트 ------------- t_sse_candidates
       └─ LLM 생성 ----------------------- t_llm
       └─ AI 결과 검증/저장 --------------- t_result_db
          └─ SSE 완료 이벤트 ------------- t_sse_complete
```

| 측정 지표 | 시작점 | 종료점 |
|---|---|---|
| 검색 처리시간 | Embedding 처리 시작 | 후보 재평가 완료 |
| 분석 처리시간 | LLM 요청 시작 | LLM 결과 생성·형식 검증 완료 |
| 후보 첫 표시까지 | 사용자가 분석 요청 | SSE 후보 이벤트 도착 |
| 최종 결과 표시까지 | 사용자가 분석 요청 | SSE 완료 이벤트 도착 |
| 대기시간 | 작업 접수 완료 | 백그라운드 실행 시작 |
| Qdrant 인덱싱 지연 | RESOLVED+작업 PENDING 커밋 | 최신 벡터 검색 가능 |

> 초기 성능 목표의 검색 구간에는 임베딩·Qdrant·JEV/Reranker가 포함된다. 후보 원본 조회가 재평가에 필요하므로 그 구간도 따로 계측한다. DB 저장 구간을 SLA에 포함할지는 실측 뒤 요구사항 문서에 명시한다.

## 4. 단계별 테스트 시나리오

| 시험 | 설정 | 확인할 항목 |
|---|---|---|
| T01 단일 검색 | 동시 1건, 정상 데이터 | `t_embed`, `t_qdrant`, `t_fetch`, `t_rerank` |
| T02 단일 LLM | 동일 후보 집합, 동시 1건 | 첫 토큰 시간(가능 시), 전체 생성시간, 출력 토큰 수 |
| T03 전체 분석 | 검색부터 SSE 완료까지 1건 | 종단 간 시간, 상태 전이, 후보 선표시 |
| T04 동시 접수 | 분석 요청 5건 동시 제출 | 접수 성공률·큐 대기·중복 Analysis 발생 여부 |
| T05 동시 실행 | 실제 Worker 1개/복수 구성 비교 | 처리량, 메모리, p95, 대기시간 |
| T06 데이터 증가 | 품질사례 크기를 단계적으로 증가 | Qdrant 조회·DB 조회 변화 |
| T07 장애·재시도 | Embedding/Qdrant/LLM 중단 및 재시작 | 성공률, 재처리 횟수, 상태 보존, 복구 소요시간 |
| T08 인덱싱 지연 | RESOLVED 처리 후 검색 가능해질 때까지 | 10분 목표와 실패·지연 건수 |
| T09 SSE 끊김 | 후보 이벤트 전후 연결 해제 후 복귀 | 작업 지속, 상태 복원, 이벤트 중복 표시 |

- 초기 실험은 **워밍업 이후** 정상 요청을 충분히 반복하되, 표본이 작을 때 p95를 과도하게 확신하지 않는다.
- 비교할 때는 가능한 한 같은 데이터, 같은 장비, 같은 모델 입력을 사용한다.
- 동시 접수 5건에 성공했다고 동시 LLM 실행 5건이나 15초 목표를 달성했다고 판단하지 않는다.

## 5. 수집할 지표

### 시간
- 검색/분석/종단 간 시간의 평균, 중앙값(p50), p95, 최댓값
- 큐 대기시간, 후보 SSE 전달 지연, 결과 DB 기록 시간

### 안정성
- 총 요청 건수 / 접수 실패 / 최종 완료 / 최종 실패 / 타임아웃 / 재시도 건수
- 재시도로 복구한 건수와 최종 실패 건수를 분리
- SSE 재연결 후 후보/결과 누락·중복 여부

### 자원
- 시스템 전체 및 컨테이너별 메모리 사용량의 **최댓값**
- CPU/GPU 사용률, OOM 발생, 스왑 사용, 디스크 및 DB I/O
- Qdrant 컬렉션 크기와 MySQL 저장량 변화

### 품질(성능 지표와 별도)
- 검색 후보의 유효성, 취소/삭제 사례 제외 여부
- JEV/Reranker 채택·제외 결과, 근거 부족 건수
- LLM 형식 검증 실패·근거 없는 사례 ID 참조 빈도

## 6. 합격/보류 판정 기준

| 판정 | 의미 |
|---|---|
| 잠정 합격 | 같은 조건의 테스트에서 검색 p95 3초, LLM p95 15초, 전체 메모리 16GB, 기능·데이터 정합성 조건을 충족 |
| 부분 합격 | 단일 요청 목표는 충족했으나 5건 동시 요청에서 대기시간이나 실패율 악화 |
| 보류 | 표본 수 부족, 모델 미확정, 측정 구간이 불분명함 |
| 개선 필요 | 초과 지표 또는 장애·데이터 불일치가 재현됨 |

**중요:** 서비스별 오류 때문에 일부 작업이 `FAILED`가 되었더라도, 성공한 요청만 집계한 응답시간이 빠르다는 이유로 합격시키지 않는다. 실패율과 시간 목표를 함께 검토한다.

## 8. 병목 원인별 검토 방향 (실측 이후)

| 확인된 병목 | 먼저 확인할 것 |
|---|---|
| 임베딩이 느림 | 모델 크기, 배치, 초기 로딩/워밍업, CPU/GPU |
| Qdrant가 느림 | Top-K, 컬렉션 크기, payload 필터, 인덱스 설정 |
| Candidate DB 쓰기가 느림 | 트랜잭션 횟수, 건별/배치 저장, DB I/O |
| JEV/Reranker가 느림 | 후보 수, 모델 크기, 입력 길이 |
| LLM이 느림 | 생성 토큰 수, 모델·양자화, context 크기, 동시 실행 수 |
| SSE가 늦게 도착 | 서버 이벤트 전송 시점, 프록시 버퍼링(도입 시), 연결 상태 |
| 동시 요청에서만 느림 | 큐 대기, Worker 수, CPU/GPU·메모리 경합 |

## 9. 이번 단계에서 확정하지 않는 것

- 측정 전 모델 선정, 상세한 하드웨어 사양별 성능 보장
- 3초·15초 목표의 변경 여부
- 부하 도구와 수집 스택(Prometheus/Grafana 등) 선택
- 최대 허용 오류율·복구 시간의 최종 SLO
- SSE 이벤트별 상세 스키마와 워커 병렬도

**원칙:** 먼저 구간별 실측과 장애 실험을 수행하고, 결과에 따라 요구사항·HLD·LLD 및 ADR을 수정한다.
