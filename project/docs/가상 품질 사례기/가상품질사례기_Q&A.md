# 가상 품질 사례 생성기 — Q&A

확정 내용은 `가상품질사례기_설계_확정안.md`. 2026-11-11 문답.

## Q1. 생성기의 목적이 로드맵과 같은가?

로드맵의 생성기는 부하 측정(메모리·응답 시간·동시 10건 p95 → 임베딩 분리 판단)이었고, 검토 요청 문서는 검색 품질 평가였다. 부하 측정에는 LLM과 현실성이 필요 없고 건수·토큰 길이만 필요하다. 둘을 한 도구로 묶으면 부하 측정이 LLM 생성 품질 문제를 기다리게 된다.
→ 평가용으로 범위를 좁혔다. 부하 측정은 동시 트래픽이 많은 서비스가 아니라서 후순위.

## Q2. 평가는 분석 API(전체 흐름)로 하는 게 좋은가, `/similar-cases`로 하는 게 좋은가?

`AnalysisWorker`와 `/similar-cases`는 검색 핵심이 같다(`toQueryText`→`embedQuery`→Qdrant top-10). 지금은 JEV·LLM이 없어서 전체 흐름으로 돌려도 검색 순위 외에 더 재는 것이 없다. `/similar-cases`는 바로 순위·점수를 주고 몇 번이든 재실행할 수 있는 반면, 분석 API는 202 후 폴링이고 재요청하면 이전 Analysis를 지운다.
→ 지금은 `/similar-cases`. JEV·LLM이 붙으면 "후보 중 무엇을 골랐나"를 재야 하므로 그때 분석 API로 같은 평가셋을 돌린다.

## Q3. NORMAL·SIMILAR·CONFUSING을 사례 유형으로 생성하면 안 되는가?

"유사"는 무엇과 비슷한지 기준이 있어야 성립하는 관계다. 사례를 하나씩 유형만 붙여 만들면 생성 뒤에 AI가 다시 짝지어야 하고, 정답표가 틀어질 수 있다.
→ 클러스터 단위로 생성하고, 정답·혼동 관계는 생성 전 계획에서 정한다.

## Q4. 평가 질의에 원인이 들어가도 되는가?

실제 검색 쿼리는 OPEN 사례 텍스트(`toQueryText`: 공정/설비/제품/증상/관찰)이고 원인·조치가 없다. 질의에 원인을 쓰면 실제보다 쉬운 문제가 되어 점수가 부풀려진다. 또 `/similar-cases`는 자유 문장이 아니라 등록된 사례 id를 받으므로 질의도 OPEN 사례로 등록해야 한다.
→ 질의는 OPEN 형식, 원인 없음. "~는 이력 없음" 같은 부정 조건은 관찰에 들어갈 수 있다.

## Q5. AI가 만든 시나리오를 AI가 검증하는 것으로 충분한가?

같은 계열 LLM에게 "타당한가"를 물으면 대부분 예라고 답할 가능성이 크다(일반적 경향, 미측정). 규칙을 대량으로 쓰지 않고 보완하는 방법: 카탈로그를 AI가 만들고 사람이 한 번만 검토, 코드로 되는 검사는 코드로, LLM은 시나리오를 보여 주지 않고 본문에서 원인을 역추출해 비교, 사람은 정답표만 본다.

## Q6. 클러스터 몇 개로 끝까지 돌려 보는 건 무엇을 검증하는가?

데이터 품질이 아니라 흐름이다. (1) 생성 JSON이 백엔드 검증을 통과하고 적재·id 대응·재실행·인덱싱 대기·질의 등록이 되는가, (2) 지표 계산이 손 계산과 같은가, (3) 평가 설계가 의미 있는가(너무 쉽지 않은가, 혼동 사례가 실제로 혼동을 일으키는가, 질의에 원인이 새지 않는가). 대량 생성 뒤에 발견하면 전부 다시 만들어야 하는 것들을 10건으로 미리 잡는다.

## Q7. 데이터가 적은데 수확이 있었는가?

흐름·설계 쪽은 확실하다: 파이프라인 동작, 코드 수정 없는 DB 분리, `searchable` 포인트 수로 인덱싱 완료 판단, 지표 검증, 혼동 제목·공정 간 클러스터·Recall@10에 대한 교훈. 검색 성능 숫자는 약하다: 질의 6개, 정답을 아는 작성자가 쓴 데이터. 정답과 혼동 점수 차가 모두 ±0.06 이내였다는 관찰만 기존 벤치마크와 같은 방향으로 뒷받침된다.

## Q8. 가중치는 어떻게 줬는가?

없다. 점수는 Qdrant 코사인 유사도 그대로이고, 사례는 필드를 이어 붙인 텍스트 하나로 임베딩하므로 필드별 가중치가 없다(다만 긴 필드가 벡터에 더 크게 반영되는 사실상의 가중치는 생긴다). 지표는 질의마다 같은 비중으로 평균했다.
→ 가중치는 나중에 검토.

## Q9. 정답 사례와 미등록(질의) 사례를 다른 모델로 써야 작성자 편향을 막는가?

편향의 핵심은 질의 작성기가 정답 사례 문장을 보고 표현을 옮기는 것이다. 이건 모델을 바꿔도 문장을 보는 한 남는다.
→ 필수는 정보 분리(작성기마다 계획의 개념만 주고 다른 사례 문장은 주지 않음). 다른 모델은 선택 사항이고, 같은 모델·다른 모델로 질의 일부를 만들어 정답 점수와 단어 겹침 비율을 비교한 뒤 정한다. GPU PC에서 사례를 전부 만든 뒤 질의를 만드는 식으로 순서대로 돌리면 두 모델을 동시에 올릴 필요는 없다.
