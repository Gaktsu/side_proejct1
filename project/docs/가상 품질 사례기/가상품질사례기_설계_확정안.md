# 가상 품질 사례 생성기 — 설계 확정안

검토 요청 원문은 `가상품질사례기_설계.md`, 문답은 `가상품질사례기_Q&A.md`. 2026-11-11 기준이며, 이 문서에 없는 내용은 아직 정하지 않았다.

## 1. 목적과 범위

- **목적은 검색 품질 평가다.** 시스템이 AI가 만든 가상 사례 사이에서 정답 사례를 상위에 올리고, 혼동 사례(부정 조건)를 정답 위로 올리지 않는지 잰다.
- 부하 측정(메모리·응답 시간·동시 요청)은 범위 밖이다. 동시 트래픽이 많은 서비스가 아니라고 보고 후순위로 미뤘다. 필요해지면 LLM 없이 템플릿으로 만든 별도 도구로 한다.
- 대량 생성은 노트북이 아닌 GPU PC에서 한다. 생성용 LLM은 그때 PC 사양을 기준으로 고른다(미정).
- 기존 백엔드 코드와 엔티티는 바꾸지 않는다. 생성기는 REST API만 호출한다.

## 2. 확정 사항

| 항목            | 결정                                                                                                                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 평가 경로       | `GET /api/quality-cases/{id}/similar-cases` (임베딩→Qdrant→MySQL 필터 전체). 모델 직접 평가는 완성 후 재검토                     |
| 분석 API로 평가 | 지금은 안 함. 검색 핵심이 `/similar-cases`와 같다(`toQueryText`→`embedQuery`→top-10). JEV·LLM이 붙으면 선별 평가용으로 추가 검토 |
| 생성 단위       | 클러스터 = 기준(ANCHOR) + 유사(SIMILAR) + 혼동(CONFUSING). 정답·혼동 관계는 생성 전 계획에서 정한다                              |
| 클러스터 배치   | 같은 공정·같은 불량 안에 클러스터 여러 개 + 같은 공정의 다른 불량 잡음(NOISE)                                                    |
| 평가 질의       | 백엔드에 OPEN 사례로 등록(resolve 안 함 → Qdrant에 안 들어감). 원인·조치 없음                                                    |
| 조사 과정 필드  | 생성하지 않음 (`investigationDetails`에 대응하는 필드가 없음)                                                                    |
| 정보 분리       | 각 작성기는 계획의 개념만 받고 다른 사례의 문장은 보지 않는다 (4절)                                                              |
| 작성 모델 분리  | 선택 사항. 같은 모델·다른 모델로 질의 일부를 만들어 비교한 뒤 정한다                                                             |
| 평가 메타데이터 | 생성기 파일에만 둔다. 백엔드에 보내지 않으므로 임베딩 텍스트에 섞일 경로가 없다                                                  |
| 평가 환경       | 별도 DB `iot_system_eval` + 별도 컬렉션 `quality_case_vectors_eval` + 포트 8081. 환경변수만 바꿈                                 |
| 구현 언어       | Python (`scripts/synthetic_cases/`)                                                                                              |
| 가중치          | 지금은 없음. 사례 텍스트 하나로 임베딩하므로 필드별 가중치를 줄 구조가 아니다. 나중에 검토                                       |

## 3. 처리 흐름

```text
[0. 카탈로그 생성]   AI → 사람 1회 검토 → catalog (공정→설비→불량→원인 트리, 제품)
        ↓
[1. 클러스터 계획]   카탈로그에서 샘플링 → plan (정답·혼동 관계 확정)
        ↓
[2. 사례 작성]       LLM, 백엔드 필드 형식 → cases.json      ← 4절 정보 분리
        ↓
[3. 검증]            결정적 검사 → LLM 역추출 비교 → 실패는 재요청/폐기/검토 폴더
        ↓
[4. 평가 질의 작성]  LLM, OPEN 형식 → eval.json              ← 4절 정보 분리
        ↓
[5. 사람 검토]       eval.json만 (정답표가 틀리면 지표 전체가 무의미)
        ↓
[6. 적재]            기준 정보(코드로 재사용) → create → resolve → out/id-map.json
        ↓
[7. 인덱싱 대기]     Qdrant searchable=true 포인트 수 = 사례 수
        ↓
[8. 평가]            질의별 /similar-cases → 순위표와 지표
```

0~5단계는 생성기(GPU PC, 미구현), 6~8단계는 `run_eval.py`(구현됨)가 맡는다. 두 단계는 `cases.json`·`eval.json` 형식으로만 연결된다.

## 4. 정보 분리 (작성자 편향 방지)

작성기가 정답 사례 문장을 보면서 질의를 쓰면 표현이 그대로 옮겨져 단어 일치로 검색이 쉬워진다. 모델을 바꿔도 문장을 보는 한 남는 문제라서, 모델 분리보다 먼저 적용한다.

| 작성 대상   | 받는 정보                                       | 받지 않는 정보       |
| ----------- | ----------------------------------------------- | -------------------- |
| 정답 사례   | 공정, 불량, 원인, 관찰 가능한 단서              | —                    |
| 혼동 사례   | 자기 원인, 부정할 원인 개념("금형 수정은 아님") | 정답 사례 문장       |
| 질의 (OPEN) | 공정, 불량, 관찰 가능한 단서                    | 원인, 정답 사례 문장 |

- 제목도 역할끼리, 질의와 겹치지 않게 따로 쓴다. 흐름 검증 1차에서 혼동 사례 제목을 정답과 같게 썼더니 부정문 판별과 제목 일치가 구분되지 않았다.
- 편향 점검 지표로 질의와 정답 사이의 단어 겹침 비율을 추가한다(미구현).

## 5. 데이터 형식

`scripts/synthetic_cases/cases.json`, `eval.json`이 기준 형식이다. 백엔드 요청 필드에 생성기 필드를 붙인다.

- 공통 백엔드 필드: `productCode`·`processCode`·`equipmentCode`(코드로 참조, 적재 때 id로 바꿈), `lotNo`, `title`, `problemDescription`, `defectType`(최대 50자), `productionQuantity`, `defectQuantity`, `occurredAt`
- 사례만: `rootCause`, `correctiveAction`, `resultSummary`(임베딩 제외 필드)
- 생성기 필드: 사례 `genId`·`clusterId`·`role`, 질의 `queryId`·`clusterId`·`relevant`·`confusing`
- 정답 ID는 생성기 ID(`genId`)다. `caseCode`는 서버가 만들므로 쓸 수 없고, 서버 id와의 대응은 `out/id-map.json`에 둔다.
- 사례 텍스트는 1024 토큰 이하여야 한다. 넘으면 resolve가 400으로 실패한다.
- 코드·LOT 접두사는 `SYN-`. `TEST-`는 자동 테스트 전용이라 쓰지 않는다.

## 6. 검증 (생성기, 미구현)

- 결정적 검사(코드): 스키마, 필수 필드, 길이, 토큰 수, 시나리오 핵심 값이 본문에 들어갔는지, 중복(같은 임베딩 모델 cosine)
- LLM 역추출: 시나리오를 보여 주지 않고 사례 본문만으로 원인을 뽑게 해 계획과 비교한다. 효과는 측정해 봐야 한다.
- 사람: 평가용 정답·혼동 쌍만 본다.
- 실패 처리: 형식 오류는 오류를 붙여 재요청, 의미 오류는 폐기, 반복 실패는 검토 폴더. 재시도 횟수는 미정.

## 7. 평가 실행 (`run_eval.py`, 구현됨)

```bash
# 평가용 앱 (코드 수정 없음)
SPRING_DATASOURCE_URL='jdbc:mysql://localhost:3306/iot_system_eval?serverTimezone=Asia/Seoul' \
QDRANT_COLLECTION=quality_case_vectors_eval SERVER_PORT=8081 ./gradlew bootRun

python3 scripts/synthetic_cases/run_eval.py
```

- 다시 실행하면 `out/id-map.json`에 있는 사례·질의는 건너뛴다. 한 건마다 기록하므로 중간에 실패해도 이어서 실행할 수 있다.
- 인덱싱 대기는 사례 응답의 `qdrantStatus=COMPLETED`로는 부족하다. 검색 노출(`searchable`)은 별도 job이 바꾸므로 Qdrant에서 `searchable=true` 포인트 수를 센다.
- 지표: Recall@1·@3·@10, MRR, 혼동 역전 수(혼동 사례가 정답보다 위), 정답−혼동 점수 차. 질의마다 같은 비중으로 평균한다.
- 데이터를 바꿔 처음부터 다시 돌리려면 수동으로 초기화한다: `DROP/CREATE DATABASE iot_system_eval` → Qdrant `DELETE /collections/quality_case_vectors_eval` → `out/id-map.json` 삭제 → 앱 재기동. `iot_system_eval` 생성과 `devuser` 권한 부여는 root로 한 번 했다.

## 8. 흐름 검증 결과 (2026-11-11, 직접 작성한 데이터)

| 차수 | 데이터                                              | Recall@1 | Recall@3 | MRR   | 혼동 역전 | 평균 점수 차 |
| ---- | --------------------------------------------------- | -------- | -------- | ----- | --------- | ------------ |
| 1차  | 9건, 질의 3, 공정별 클러스터 1개, 혼동 제목=정답    | —        | —        | 0.833 | 1/3       | —            |
| 2차  | 27건, 질의 6, 공정별 클러스터 2개 + 잡음, 제목 독립 | 0.667    | 1.000    | 0.833 | 2/6       | +0.007       |

얻은 것:

- 적재부터 지표까지 흐름이 동작하고, 다시 실행해도 중복 등록이 없다. 지표 계산은 손 계산과 일치했다.
- 제목을 달리해도 혼동 사례가 6개 질의 모두에서 2위 안이고 정답과 점수 차가 ±0.06 이내였다. 기존 벤치마크의 부정 대조쌍 결과(1/5)와 같은 방향이다. 원인 판별을 JEV·LLM에 맡긴 설계 판단의 근거가 된다.
- 공정이 다른 사례는 점수가 0.52 이하라 방해가 되지 않았다. 같은 공정 사례는 0.63~0.81로 실제 방해 역할을 했다 → 같은 공정·같은 불량 안에 클러스터를 여러 개 둔다.
- 사례가 10건 이하이면 Recall@10은 항상 1.0이다.

한계:

- 질의가 6개라 순위 하나가 지표를 0.17씩 움직인다. 숫자 자체는 믿을 수 없다.
- 사례와 질의를 정답을 아는 한 작성자가 썼다(작성자 편향). 그래서 이번 결과는 "평가를 할 수 있는 상태를 만든 것"이고 평가 결과가 아니다.

## 9. 미결정 사항

| 우선순위 | 항목                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| 상       | 생성용 LLM (GPU PC 기준, 한국어 제조 용어 품질, JSON 형식 준수율)                |
| 상       | 카탈로그 형식과 사람 검토 방법                                                   |
| 중       | 클러스터 수·크기, 질의 수 (지표가 안정되려면 수십~수백 개)                       |
| 중       | 작성 모델 분리 여부 (측정 후), 재시도 횟수, 사람 검토 비율, 중복 cosine 기준값   |
| 중       | 단어 겹침 비율 지표, 초기화를 스크립트에 넣을지                                  |
| 하       | 필드별 가중치, 모델 직접 평가 경로, 등급식 정답(유사 사례를 부분 정답으로, nDCG) |
