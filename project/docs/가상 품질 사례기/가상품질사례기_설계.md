# AI 기반 가상 품질 사례 생성기 — 상세 설계 검토 요청

## 1. 프로젝트 배경

현재 **「AI 기반 품질사례 지식화 및 원인조사 지원 시스템」**이라는 개인 백엔드 프로젝트를 개발하고 있다.

이 프로젝트는 제조업에서 발생한 품질 불량 사례를 체계적으로 관리하고, 과거 유사 사례를 검색하여 AI가 원인 조사와 해결을 지원하는 시스템이다.

### 기존 시스템의 주요 기능

1. 품질 사례 등록 및 관리
2. 임베딩 기반 유사 품질 사례 검색
3. RAG 및 LLM을 이용한 원인 분석 지원
4. 담당자의 원인 및 조치 결과 확정
5. 해결된 품질 사례의 비동기 인덱싱
6. 축적된 과거 사례를 활용한 신규 품질 문제 분석

### 기존 기술 구성

- Backend: Java / Spring Boot
- Database: MySQL
- Vector Database: Qdrant
- AI: 한국어 임베딩 모델 및 LLM
- Communication: REST API, SSE
- Infrastructure: Docker / Docker Compose

현재 시스템의 핵심 처리 흐름은 다음과 같다.

```text
품질 사례 등록
    ↓
유사 사례 검색
    ↓
LLM 기반 원인 조사 지원
    ↓
담당자의 원인 및 조치 확정
    ↓
RESOLVED 상태 전환
    ↓
IndexingJob 생성
    ↓
비동기 임베딩 및 Qdrant 인덱싱
    ↓
향후 유사 사례 검색에 활용
```

기존 시스템의 설계와 비즈니스 규칙은 가능한 한 유지할 계획이다.

# 2. 가상 품질 사례 생성기가 필요한 이유

현재 시스템은 과거 품질 사례를 기반으로 유사 사례를 검색하는 구조다.

하지만 실제 제조업의 품질 불량 데이터를 대량으로 확보하기 어렵다.

이로 인해 다음과 같은 문제가 발생한다.

1. 유사 사례 검색을 충분한 데이터로 테스트하기 어렵다.
2. 임베딩 모델별 검색 성능을 비교하기 어렵다.
3. 서로 비슷하지만 원인이 다른 사례를 충분히 확보하기 어렵다.
4. 부정문이나 상반된 조건에서 검색 모델이 올바르게 작동하는지 검증하기 어렵다.
5. 데이터가 부족하면 RAG 시스템의 전체 처리 흐름을 검증하는 데 제약이 발생한다.

따라서 **제조업 품질 사례를 자동으로 대량 생성하는 독립적인 도구**를 개발하려고 한다.

생성된 데이터는 합성 데이터이며, 실제 제조업에서 발생한 사례라고 주장하지 않는다.

또한 합성 데이터만을 이용한 평가 결과를 실제 산업 현장에서의 성능으로 일반화하지 않는다.

# 3. 현재까지 확정한 설계 방향

## 3.1. 핵심 생성 방식

현재 선택한 방식은 다음과 같다.

**AI 기반 시나리오 생성 → 시나리오 검증 → LLM 사례 구체화 → 최종 검증 → JSON 저장**

초기에는 규칙 기반 생성과 LLM을 결합하는 방식을 고려했다.

하지만 제품, 공정, 설비, 불량 유형, 발생 원인 간의 관계를 사용자가 직접 대량으로 정의하는 것은 부담이 크다고 판단했다.

따라서 다음과 같이 설계를 변경했다.

- 제조업 시나리오는 AI가 자동으로 생성한다.
- AI가 생성한 시나리오는 별도 검증 과정을 거친다.
- 검증된 시나리오를 바탕으로 LLM이 상세 사례를 작성한다.
- 프로그램은 생성 과정, JSON 구조, 오류 처리, 중복 확인 등을 관리한다.
- 제조업 관련 규칙을 사용자가 일일이 작성하는 방식은 지양한다.

단, 모든 검증을 LLM에만 의존하는 것이 적절한지는 아직 결정하지 않았다.

이 부분은 상세 설계 과정에서 검토하고 싶다.

## 3.2. 전체 처리 흐름

```text
[사용자]
생성 개수 및 조건 설정
         │
         ▼
[1. AI 기반 시나리오 생성]
제품 / 공정 / 설비 / 불량 유형 / 발생 원인
         │
         ▼
[2. 시나리오 검증]
제조업 타당성 / 논리적 모순 / 중복 검사
         │
         ▼
[3. LLM 기반 품질 사례 구체화]
불량 현상 / 조사 과정 / 원인 / 조치 / 결과
         │
         ▼
[4. 최종 데이터 검증]
구조 / 조건 준수 / 논리적 일관성 / 중복 검사
         │
         ├── 검증 실패
         │      ├── 재생성
         │      └── 검토 대상으로 분류
         │
         ▼
[5. JSON 데이터 저장]
         │
         ▼
[6. 기존 Spring Boot 백엔드]
품질 사례 등록
         │
         ▼
[7. MySQL]
품질 사례 저장
         │
         ▼
[8. 기존 RAG 시스템]
RESOLVED → 비동기 인덱싱 → Qdrant
```

이 흐름은 현재 상위 설계안이며, 세부 단계의 순서나 책임 분리는 개선할 수 있다.

다만 변경을 제안한다면 기존 방식의 문제점과 변경 이유를 먼저 설명해 달라.

# 4. 주요 구성 요소

현재 다음과 같은 구성 요소를 생각하고 있다.

| 구성 요소 | 역할 |
|---|---|
| 생성 조건 관리 | 생성 수량, 제조업 분야, 사례 유형 설정 |
| AI 시나리오 생성기 | 제품·공정·설비·불량·원인 조합 생성 |
| 시나리오 검증기 | 제조업 타당성 및 논리적 모순 검증 |
| LLM 사례 작성기 | 불량 현상, 조사 과정, 원인, 조치 및 결과 생성 |
| 최종 검증기 | JSON 구조, 조건 준수, 내용 일관성 및 중복 검사 |
| 데이터 출력 | 검증된 품질 사례를 JSON으로 저장 |
| 백엔드 연계 | 생성 데이터를 기존 품질 사례 등록 기능에 전달 |
| 평가 데이터 관리 | 검색 질문, 정답 사례, 혼동 사례 관계 관리 |

각 구성 요소는 역할이 명확하게 분리되기를 원한다.

다만 지나치게 복잡한 아키텍처나 불필요한 추상화는 피하고 싶다.

개인 프로젝트이므로 구현 가능성과 유지보수성을 고려해야 한다.

# 5. 데이터 생성 유형

가상 사례는 다음 세 가지 유형으로 구분하려고 한다.

## 5.1. 일반 사례

다양한 제조업 품질 불량 사례를 생성한다.

예시:

- 제품: 플라스틱 하우징
- 공정: 사출 성형
- 불량: 휨 변형
- 원인: 냉각 시간 부족

목적은 다양한 품질 사례 데이터를 확보하는 것이다.

## 5.2. 유사 사례

불량 현상은 비슷하지만 발생 원인이 다른 사례를 생성한다.

예시:

- 사례 A: 냉각 시간 부족으로 휨 변형 발생
- 사례 B: 금형 냉각 불균형으로 휨 변형 발생

목적은 검색 시스템이 유사한 현상 속에서 원인과 조건의 차이를 구분하는지 평가하는 것이다.

## 5.3. 혼동 사례

의미적으로 비슷하지만 실제 조건이 다르거나, 부정문 때문에 검색 모델이 혼동할 수 있는 사례를 생성한다.

예시:

- 사례 A: 금형 형상 변경으로 휨 변형 발생
- 사례 B: 금형 형상 변경 이력은 없으며, 냉각 시간 부족으로 휨 변형 발생

이전에 임베딩 모델을 비교하면서 부정문에 포함된 원인을 잘못 해석하여 혼동 사례를 정답보다 높은 순위에 배치하는 문제가 발견되었다.

따라서 이러한 상황을 평가하기 위한 데이터를 의도적으로 생성하고 싶다.

특히 일반·유사·혼동 사례가 서로 어떤 관계를 가져야 하는지, 평가용 데이터를 어떻게 구성해야 하는지 검토해 달라.

# 6. 생성 데이터 예시

## 6.1. 사용자 입력

```json
{
  "industry": "자동차 부품 제조업",
  "count": 30,
  "caseTypes": [
    "NORMAL",
    "SIMILAR",
    "CONFUSING"
  ]
}
```

사용자가 설정하는 조건은 최소화하고 싶다.

제품, 제조 공정, 설비, 불량 유형, 원인 등을 사용자가 일일이 정의하는 방식은 피하고 싶다.

## 6.2. AI 시나리오 생성 결과

```json
{
  "product": "플라스틱 하우징",
  "manufacturingProcess": "사출 성형",
  "equipment": "사출 성형기",
  "defectType": "휨 변형",
  "rootCause": "냉각 시간 부족"
}
```

이 단계에서는 상세 사례 문장을 생성하기보다 핵심 조건을 먼저 결정한다.

## 6.3. LLM 상세 사례 생성 결과

```json
{
  "caseCode": "CASE-001",
  "product": "플라스틱 하우징",
  "manufacturingProcess": "사출 성형",
  "equipment": "사출 성형기",
  "status": "RESOLVED",
  "defectDescription": "사출 성형 후 제품 우측 모서리에서 휨 변형이 발생하였다.",
  "investigationDetails": "금형 형상 변경 이력은 없었으며, 냉각 시간이 기준보다 짧게 설정되어 있었다.",
  "rootCause": "냉각 시간 부족으로 인한 불균일한 수축",
  "correctiveAction": "냉각 시간을 기준값으로 조정하였다.",
  "verificationResult": "조정 후 생산된 제품에서 동일한 휨 변형이 관찰되지 않았다."
}
```

이 JSON은 현재 설명을 위한 예시다.

실제 백엔드 DTO나 DB 엔티티와 정확히 일치하는 구조는 아니다.

상세 설계 시에는 기존 프로젝트의 데이터 모델을 확인하고 적절한 형태로 변경해야 한다.

# 7. 데이터 검증 설계

현재 검증은 두 단계로 구분했다.

## 7.1. 시나리오 검증

AI가 생성한 제품·공정·설비·불량·원인 조합을 검증한다.

검증 대상:

- 제조업 분야에 적합한 제품인가?
- 해당 제품에 적용 가능한 제조 공정인가?
- 해당 공정에서 사용할 수 있는 설비인가?
- 해당 공정에서 발생 가능한 불량인가?
- 해당 불량과 발생 원인 사이에 인과관계가 성립하는가?
- 기존에 생성한 시나리오와 불필요하게 중복되지 않는가?

## 7.2. 최종 사례 검증

LLM이 작성한 내용을 검증한다.

검증 대상:

- 필수 정보가 모두 존재하는가?
- JSON 구조가 올바른가?
- 최초 시나리오의 핵심 조건이 유지되었는가?
- 불량 현상과 발생 원인이 일치하는가?
- 조사 내용이 발생 원인을 뒷받침하는가?
- 조치 내용이 발생 원인에 대응하는가?
- 조치 결과가 앞선 내용과 모순되지 않는가?
- 기존 사례와 과도하게 중복되지 않는가?

## 7.3. 검증 실패 처리

현재 생각하는 방식은 다음과 같다.

- 수정 가능한 오류: 재생성
- 반복적으로 검증에 실패한 사례: 별도 검토
- 자동 판단이 불확실한 사례: 별도 검토
- 검증을 통과한 사례: JSON 저장 및 백엔드 등록 대상으로 분류

다만 재시도 횟수, 검증 기준, 자동 승인 조건은 아직 정하지 않았다.

### 특히 검토받고 싶은 부분

AI가 생성한 시나리오를 또 다른 AI가 검증하는 것만으로 충분한가?

만약 부족하다면, 사용자가 제조업 규칙을 직접 대량으로 정의하지 않으면서도 데이터의 타당성을 높일 수 있는 현실적인 설계는 무엇인가?

이 부분을 중점적으로 분석해 달라.

# 8. RAG 평가 데이터 설계

품질 사례 생성과 별도로 검색 성능 평가에 사용할 데이터도 생성하려고 한다.

필요한 정보는 다음과 같다.

- 검색 질문
- 관련 있는 품질 사례
- 정답 사례 ID
- 혼동 사례 ID
- 사례 간 관련성 정보

예를 들어 다음과 같은 평가를 수행할 수 있어야 한다.

```text
검색 질문:
"금형 형상 변경 이력은 없지만
냉각 시간이 부족하여 휨 변형이 발생한 사례"

정답:
CASE-001

혼동 사례:
CASE-002
```

생성된 검색 질문과 정답 관계를 이용하여 Recall@K, MRR, nDCG@K 등의 지표로 검색 성능을 평가하는 것을 고려하고 있다.

다만 평가 데이터의 정답을 AI가 함께 생성하면 정답 자체가 잘못되거나, 평가 질문이 지나치게 단순해질 가능성이 있다.

따라서 다음 사항을 검토해 달라.

- 검색 평가용 정답을 생성하는 적절한 시점
- 정답과 혼동 사례의 관계를 검증하는 방법
- 생성 데이터의 편향을 줄이는 방법
- 일반 사례와 평가용 사례를 분리할 필요성
- 정답 정보가 임베딩 텍스트에 포함되지 않도록 하는 방법

# 9. 기존 백엔드와의 연계 조건

가상 사례 생성기는 기존 백엔드와 독립적으로 구성하고 싶다.

기존 백엔드는 다음 책임을 유지한다.

- 품질 사례 등록
- 엔티티 관계 및 참조 무결성 관리
- QualityCase 상태 관리
- RESOLVED 전환
- IndexingJob 생성
- 비동기 임베딩 및 Qdrant 인덱싱

생성기는 검증된 JSON 데이터를 전달하는 역할을 담당한다.

기존 도메인 엔티티를 생성기 요구사항에 맞춰 불필요하게 변경하지 않기를 원한다.

특히 평가용 메타데이터와 실제 품질 사례 데이터를 분리하여, 평가 정답 정보가 검색 결과에 영향을 주지 않도록 설계하고 싶다.

현재 백엔드의 실제 구조를 확인하지 못한 상태라면 임의로 엔티티나 API가 존재한다고 가정하지 말아 달라.

필요한 경우 현재 설계 문서나 소스코드를 요청해도 된다.

# 10. 이번 논의에서 검토할 핵심 사항

현재 설계를 무조건 긍정하지 말고, 실제 구현 가능성과 유지보수성을 기준으로 검토해 달라.

특히 다음 항목을 분석해 달라.

### A. 전체 아키텍처

- AI 시나리오 생성과 상세 사례 작성을 분리하는 것이 적절한가?
- 두 단계를 하나로 합치는 편이 더 나은 상황이 있는가?
- 생성 단계와 검증 단계의 책임 분리가 적절한가?
- 전체 구조에서 불필요하거나 누락된 단계는 무엇인가?

### B. 데이터 생성 방식

- 사용자 개입을 최소화하면서 다양한 사례를 생성할 수 있는가?
- AI가 제조업 규칙을 자동으로 생성하도록 하는 방식은 적절한가?
- 데이터 다양성과 현실성을 동시에 확보하려면 무엇이 필요한가?
- 대량 생성 시 반복되는 패턴을 어떻게 줄일 수 있는가?

### C. 데이터 검증

- AI가 만든 제조업 사례의 신뢰성을 어떤 기준으로 평가할 것인가?
- 구조 검증과 의미 검증을 어떻게 구분할 것인가?
- LLM을 이용한 자체 검증의 한계를 어떻게 보완할 것인가?
- 검증 실패 시 재생성보다 수정이 효율적인 경우가 있는가?

### D. 데이터 모델

- 시나리오 JSON과 최종 사례 JSON을 분리해야 하는가?
- 생성 과정의 메타데이터를 어느 수준까지 저장해야 하는가?
- 평가용 정답 데이터를 어떻게 관리하는 것이 적절한가?
- 기존 백엔드 DTO와의 매핑을 어떤 계층에서 처리해야 하는가?

### E. 운영 및 테스트

- 대량 생성 도중 일부 사례가 실패하면 어떻게 처리할 것인가?
- 동일 조건에서 생성 결과를 재현하거나 추적하려면 무엇이 필요한가?
- 생성 결과를 어떤 테스트로 검증할 것인가?
- 생성기 자체의 품질을 어떤 지표로 평가할 것인가?

# 11. 이번 단계에서 하지 않을 것

현재는 상세 설계를 검토하는 단계다.

따라서 다음 작업은 아직 진행하지 않는다.

1. 실제 소스코드 작성
2. 프로젝트 폴더 및 파일 생성
3. DB 스키마 변경
4. 라이브러리나 프레임워크 확정
5. 특정 LLM 모델 확정
6. Docker 또는 배포 환경 구축
7. 기존 백엔드 코드 수정
8. DOCX, HWP, HWPX 등의 문서 생성 기능 추가

기술 선택이 필요한 부분은 후보와 판단 기준을 설명하되, 현재 단계에서 임의로 확정하지 말아 달라.

# 12. 원하는 검토 및 응답 방식

다음 순서로 진행해 달라.

## 1단계: 현재 설계 평가

현재 설계에서 다음을 구분해 달라.

- 유지해야 할 설계
- 개선이 필요한 설계
- 불필요한 구성 요소
- 추가해야 할 구성 요소
- 실제 구현 시 위험한 부분

단순히 좋은 설계라고 평가하기보다 근거를 제시해 달라.

## 2단계: 대안 비교

문제가 발견되었다면 대안을 제시하고 다음 기준으로 비교해 달라.

- 데이터 생성 품질
- 제조업 사례의 현실성
- 자동화 수준
- 구현 복잡도
- 유지보수성
- 대량 생성 확장성
- RAG 평가 활용성

모든 항목을 반드시 변경할 필요는 없다.

현재 설계가 적절한 부분은 유지해도 된다.

## 3단계: 개선된 설계안 제시

검토 결과를 바탕으로 개선된 전체 처리 흐름을 제안해 달라.

각 구성 요소의 역할과 입력·출력을 명확하게 설명해 달라.

필요하면 간단한 JSON 예시도 포함해 달라.

## 4단계: 미결정 사항 정리

추후 기술 선정이나 구현 단계에서 결정해야 하는 사항을 정리해 달라.

중요도에 따라 우선순위를 구분해 달라.

# 13. 중요 지침

나는 Java 백엔드 개발을 공부하면서 이 프로젝트를 진행하고 있다.

AI의 도움을 받아 코드를 작성하더라도 **전체 시스템의 흐름, 기술 선택 이유, 데이터 구조, 오류 처리 방식은 직접 이해하고 결정하려고 한다.**

따라서 다음 원칙을 지켜 달라.

1. 내가 제시한 설계를 무조건 수용하지 말고 비판적으로 검토한다.
2. 문제가 있다면 문제의 원인과 실제 발생 가능한 상황을 설명한다.
3. 대안을 제시할 때는 장단점과 선택 기준을 함께 설명한다.
4. 아직 확정되지 않은 설계는 확정된 것처럼 표현하지 않는다.
5. 불필요하게 복잡한 아키텍처를 도입하지 않는다.
6. 개인 프로젝트 규모에서 구현 가능한 현실적인 방안을 우선한다.
7. 코드를 작성하기 전에 설계 검토를 완료한다.
8. 기존 백엔드의 비즈니스 규칙과 충돌하는 변경을 임의로 결정하지 않는다.
9. 검증되지 않은 기술적 주장이나 제조업 지식을 사실로 단정하지 않는다.
10. 개선이 필요한 부분은 중요도가 높은 순서대로 제시한다.

**우선 이번 응답에서는 현재 상위 설계를 분석하고, 가장 중요하게 개선해야 할 부분과 추천하는 전체 구조를 제시해 달라.**

구체적인 코드는 작성하지 말아 달라.

최종 목표는 단순히 JSON 데이터를 대량 생성하는 것이 아니라, **제조업 품질 사례로서 일정 수준의 일관성과 다양성을 갖추고 RAG 검색·분석 및 성능 평가에 활용할 수 있는 데이터 생성 시스템을 설계하는 것**이다.
