
> 상태: **초안(검토 중)**  
> 범위: 인트라넷 환경의 소규모 MVP. 세부 재시도 횟수·대기열 기술·모델 교체 방식은 LLD에서 결정.

## 1. 서비스 구성 요소 및 실행 환경

- **Spring Boot**: API, 인증·인가, 품질사례와 분석 작업의 흐름 조율
- **MySQL**: 공정·설비·제품·품질사례 등 원본 데이터와 분석 작업/결과 저장 (**Source of Truth**)
- **Embedding 서비스**: 해결된 품질사례 및 신규 문제 텍스트를 임베딩 벡터로 변환
- **Qdrant**: 해결된 품질사례 벡터를 보관하는 **재생성 가능한 검색 인덱스**; 신규 문제의 유사 사례 검색
- **JEV 또는 Reranker (선정 미정)**: Qdrant에서 검색한 후보 사례를 재평가·필터링·재정렬. Spring 내부 모듈 또는 별도 서비스 여부 미정
- **로컬 LLM 서비스**: 검색된 사례를 근거로 원인 후보·요약·추가 확인사항 생성
- **Docker / Docker Compose**: 서비스의 컨테이너 실행 및 내부 네트워크 구성 (비즈니스 서비스 자체는 아님)

## 2. 서비스별 역할과 책임

### Spring Boot
- 인트라넷 클라이언트의 API 요청 수신, 입력 검증 및 사용자 인증·인가
- 품질사례 CRUD, 중복 식별자 확인, 상태 변경(예: OPEN → RESOLVED) 처리
- MySQL을 원본 저장소로 사용하고, Qdrant를 검색 인덱스로 사용
- 분석 작업 생성·상태 조회, Embedding/Qdrant/JEV·Reranker/LLM 호출 흐름 조율
- AI 출력의 형식 및 근거 ID 유효성 검증, 결과 저장과 담당자 최종 판단의 구분
- 오류 유형에 따라 **재시도 가능한 일시적 실패만** 재처리; 중복 작업의 부작용 방지
- 요청 ID와 분석 작업 ID로 구간별 로그 연결

### MySQL
- 공정·설비·제품·품질사례·분석 이력 및 결과의 영속 저장
- 각 **분석 작업(Analysis 또는 전용 Job)** 단위로 PENDING/PROCESSING/COMPLETED/FAILED 등 진행 상태 보관
- 품질사례의 해결 상태와 **인덱싱 상태**를 별도로 관리할 수 있도록 설계 (필드/테이블은 LLD에서 결정)
- DB 계정 접근 권한과 사용자 역할별 API 권한은 별개로 관리

### Embedding
- 인덱싱 대상 품질사례 및 검색 질의 텍스트 → 벡터 변환
- 모델 변경 시 기존 벡터와 새 모델의 호환성 검증 및 재임베딩 계획 필요

### Qdrant
- RESOLVED 사례를 대상으로 한 벡터 인덱스 관리 (등록·수정·해제·삭제에 따른 반영 필요)
- 신규 품질 문제 벡터로 유사 후보 Top-K 검색
- 조회 결과는 MySQL 원본·상태와 대조 가능해야 하며, 인덱스 오류를 원본 데이터 손실로 취급하지 않음

### JEV 또는 Reranker
- 검색 후보를 **재검색이 아니라 재평가·재정렬·필터링**함
- 적용 방식과 배치 위치는 벤치마크 및 기술 검증 후 선정

### 로컬 LLM
- 전달받은 원본 조건과 참고 사례를 기반으로 요약·원인 후보·추가 확인사항 생성
- 최종 해결 판정은 담당자가 수행하며, 생성 결과는 검증 대상

## 3. 비동기 작업 및 데이터 일관성 — HLD 수준의 원칙

1. 사용자의 분석 요청은 작업으로 **접수**하고 상태를 조회할 수 있도록 함.
2. 별도 실행 주체(초기 후보: Spring 내부 Worker)가 작업을 처리함. 단순 스레드/메모리 FIFO만으로는 재시작 시 작업 보존을 보장할 수 없으므로 **영속적인 작업 기록**이 필요함.
3. FIFO는 아직 **미확정**. 접수 순서·실행 순서·완료 순서는 다를 수 있으며, 동시 처리 및 우선순위를 검토한 뒤 결정함.
4. MySQL 원본 저장 후 Qdrant 인덱싱은 **별도 작업**으로 처리함. MySQL 커밋과 이벤트 발행 사이에 장애가 발생해도 누락을 발견하고 복구할 수 있어야 함.
5. 인덱싱 작업 전달 보장 방식은 **미정**: DB 상태 기반 재처리, Transactional Outbox 등 비교 예정. 단순 메모리 이벤트 발행만으로는 보장되지 않음.
6. 품질사례 상태(OPEN/RESOLVED 등)와 인덱싱 상태(PENDING/COMPLETED/FAILED 등)는 구분함.
7. 재시도·중복 실행 시 동일 작업의 결과가 중복 저장되지 않도록 설계함.

## 4. 통신 관계

| 구간 | 방식 | 결정 상태 |
|---|---|---|
| 인트라넷 Client ↔ Spring | HTTPS 기반 HTTP API | **확정** |
| Spring ↔ MySQL | JDBC / JPA | **확정** |
| Spring ↔ Embedding | 내부 호출 API(예: HTTP) | 프로토콜 미정 |
| Spring ↔ Qdrant | Qdrant API | **확정** |
| Spring ↔ JEV/Reranker | Spring 내부 모듈 또는 내부 API | 미정 |
| Spring ↔ 로컬 LLM | 내부 추론 API 또는 라이브러리 호출 | 미정 |

## 5. 네트워크 및 보안 경계

- 사용자 접근은 **인트라넷 내부로 제한**, Client ↔ Spring 통신에는 **HTTPS** 적용.
- 외부 인터넷에서 서비스 접근 차단. 실제 환경에서 인트라넷 접근 통제는 방화벽/라우팅/바인딩 등으로 구성하며, Docker 네트워크만으로 이를 보장하지 않음.
- MySQL·Qdrant·Embedding·LLM은 클라이언트에게 직접 포트를 공개하지 않는 것을 기본으로 함.
- 내부 사용자도 인증·인가 대상이며, 프롬프트 인젝션·입력 검증·비밀정보 관리가 별도로 필요함.
- **Reverse Proxy(Nginx 등)는 미정**: Spring 직접 TLS 종료와 비교해 배포 단계에서 선정.
- 로컬 모델 기반으로 운영 중 외부 API 의존을 두지 않는 것을 목표로 함. 모델/패키지 설치 및 업데이트 시 네트워크 정책은 별도 검토.

## 6. 배포 및 가용성 가정

- 초기에는 Docker Compose 기반, 전체 RAM **16GB 이내**가 제약조건.
- 동시 요청 5건의 **접수** 목표와 동시 분석 실행 수는 구분하여 성능 검증 후 결정.
- Embedding 다중 인스턴스·무중단 모델 교체는 자원 제약 및 실제 필요성 검증 후 채택.
- 컨테이너 재시작에도 MySQL 원본·분석 작업/결과는 영속 보존해야 함.
