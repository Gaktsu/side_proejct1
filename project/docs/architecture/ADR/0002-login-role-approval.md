# ADR-0002: 로그인·역할과 최종 담당자 승인 구조

## 1. 상태

- **제안** (2026-10-27) — 승인 구조의 방향은 사용자 결정, 인증 방식과 단계 구분은 제안

## 2. 배경 및 문제

- NFR-07은 역할에 따라 등록·수정·조회·해결 권한을 제한하라고 하지만, 지금까지는 MVP에서 로그인·권한을 제외했다 (CLAUDE.md).
- LLD 1의 RESOLVED 수정 이력(`quality_case_revision`)은 "무엇이 언제" 바뀌었는지만 남고 "누가"를 남기지 못한다. 악의적 수정을 추적하려면 요청자가 필요하다.
- 사용자 구상: **팀원은 최종 담당자에게 승인을 요청하고, 최종 담당자가 서버 반영 여부를 결정한다.** 여러 사람이 동시에 확정 데이터를 바꾸는 일을 줄이고 책임자를 분명히 하기 위함.
- 로그인은 이 프로젝트에 필요하지만 핵심 비중은 크지 않다. 그래서 LLD 없이 이 ADR로 흐름을 정한다.

## 3. 고려한 대안

### 대안 A. 요청 헤더로 사용자·역할 전달 (`X-User-Id`, `X-Role`)

- 장점: 의존성 추가 없음, 가장 단순
- 단점: 누구나 위조 가능해 "누가"를 증명하지 못함. 나중에 전부 걷어내야 함

### 대안 B. Spring Security + 코드에 정의한 가상 사용자 + HTTP Basic (선택)

- 장점: 실제 인증 경로(`SecurityFilterChain`, 역할 기반 인가)를 그대로 쓰고, 사용자 저장소만 나중에 DB로 바꾸면 됨. 사용자 관리 기능이 필요 없음
- 단점: 사용자 추가에 코드 수정 필요. 요청자는 FK가 아닌 로그인 ID 문자열로 저장. HTTP Basic은 HTTPS 없이 비밀번호가 평문으로 오감

### 대안 C. Spring Security + `app_user` 테이블 + 세션 로그인

- 장점: 정식 사용자 관리, 요청자를 FK로 연결
- 단점: 가입·비밀번호 변경·초기 계정 주입 등 범위가 커짐. 지금 비중에 비해 과함

## 4. 최종 결정 (제안)

### 역할

| 역할       | 의미                                                      |
| ---------- | --------------------------------------------------------- |
| `MEMBER`   | 팀원. 조회·등록·분석 요청, 확정 데이터 변경은 승인 요청만 |
| `APPROVER` | 최종 담당자. 승인 요청을 검토하고 서버에 반영             |

### 1단계: 가상 사용자 + 역할 인가 (LLD 1 구현 후)

- 대안 B. 가상 사용자 몇 명(예: `member1`, `member2`, `approver1`)을 코드에 두고 비밀번호는 환경변수로 받는다 (NFR-11)
- 인가

| 작업                                                           | MEMBER | APPROVER |
| -------------------------------------------------------------- | ------ | -------- |
| 조회, 품질사례 등록, OPEN 사례 수정, 유사 사례 검색, 분석 요청 | O      | O        |
| 해결, RESOLVED 수정, 해결 취소, 삭제, 복구                     | X      | O        |
| 제품·공정·설비 등록·수정·삭제                                  | X      | O        |

- 이력에 `changed_by`(로그인 ID) 기록

### 2단계: 승인 요청 (LLD 4 이후)

- 팀원의 요청도 서버에 저장해야 담당자가 볼 수 있다 → `change_request` 테이블
  - 유형, 대상 사례, 요청 내용(JSON), `requested_by`, 상태(PENDING / APPROVED / REJECTED), `decided_by`, `decided_at`, 반려 사유
- 승인하면 같은 트랜잭션에서 실제 변경 + 이력(`requested_by`, `approved_by`) + 인덱싱 job 기록
- 승인 대상은 **확정 지식을 바꾸는 작업만**: 해결, RESOLVED 수정, 해결 취소, 삭제, 복구. 등록과 분석 요청은 바로 실행 (긴급 대응이 승인 대기로 늦어지지 않게)

## 5. 선택 이유

- 대안 B는 인가 규칙과 테스트 구조가 정식 인증과 같아서, 사용자 저장소만 바꾸면 대안 C로 옮겨 갈 수 있다.
- 대안 A는 "누가"를 증명하지 못해 이 결정의 목적(책임 추적)을 이루지 못한다.
- 대안 C는 로그인의 비중에 비해 범위가 크다.

## 6. 예상되는 영향 및 한계

- 긍정: 확정 데이터 변경의 책임자가 분명해지고, 이력에 요청자·승인자가 남는다. 동시 변경이 담당자 한 명으로 모여 충돌이 줄어든다.
- 한계
  - 동시성 문제는 줄 뿐 사라지지 않는다 (중복 클릭, 담당자 여러 명, 네트워크 재시도). 기존 락·409는 유지한다.
  - HTTP Basic은 HTTPS(NFR-10) 없이는 비밀번호가 노출된다. 실제 사용 전 HTTPS 필수.
  - 요청자가 문자열이라 사용자 이름 변경·삭제를 추적하지 못한다.
- 추가 작업
  - `spring-boot-starter-security` 추가, 기존 MockMvc 테스트 전부에 인증 부여(`@WithMockUser` 등)
  - CLAUDE.md의 "MVP에서 로그인/권한 제외" 수정
  - 승인 요청 화면·알림은 프론트 단계에서

## 7. 재검토 조건

- 사용자 추가·변경이 잦아져 코드 수정이 부담될 때 → 대안 C
- 승인 대기가 업무를 막는다는 피드백이 나올 때 → 승인 대상 축소 또는 긴급 경로
- 담당자가 여러 명이 되어 같은 요청을 동시에 승인하는 일이 생길 때 → 요청 상태에 낙관적 락
