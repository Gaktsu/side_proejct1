## 1. 상태

- **제안(검증 필요)** — 현재 선호안은 C. 이벤트 유실 방지 및 재처리 방식 확정 전까지 최종 확정하지 않음.

## 2. 배경과 문제

- MySQL은 품질사례의 **원본 데이터(Source of Truth)**, Qdrant는 RESOLVED 사례의 **검색용 인덱스**로 사용함.
- 사례가 RESOLVED가 되거나 해결된 사례의 내용이 변경되면 Qdrant 인덱스를 갱신해야 함. RESOLVED가 해제되거나 사례가 삭제될 때에도 검색 인덱스 반영이 필요함.
- MySQL 트랜잭션과 Qdrant 쓰기는 하나의 일반적인 원자적 트랜잭션으로 자동 묶이지 않음.
- 장애 발생 시 원본 데이터는 보존하고, 인덱스 누락/잔존 데이터를 탐지·복구할 수 있어야 함.
- 외부 호출 동안 MySQL 트랜잭션을 불필요하게 오래 유지하지 않도록 함.

## 3. 고려한 대안

### A. Qdrant 먼저 Upsert → MySQL 기록

- **장점:** Qdrant 저장 성공 시 벡터를 바로 확보할 수 있음.
- **단점:** 이후 MySQL 저장 실패 시 원본과 연결되지 않는 벡터가 남을 수 있음. 원본 데이터의 권위가 불명확해질 위험.
- **참고:** 저장 순서 자체가 트랜잭션 경계를 결정하지는 않음.

### B. MySQL 먼저 INSERT → Redis에 벡터 임시 보관 → Qdrant 반영

- **장점:** 벡터를 안전하게 보존·조회할 수 있다면 Qdrant 재시도 때 재임베딩을 줄일 수 있음.
- **단점:** Redis 추가에 따른 메모리·운영·영속성/복구 고려가 필요해 소규모 MVP에서는 과할 수 있음.
- **참고:** Redis 사용 여부와 MySQL 트랜잭션 분리는 별개임.

### C. MySQL 커밋 후 이벤트로 비동기 인덱싱 (현재 선호)

- **장점:** 사용자 요청과 인덱싱을 분리하며 MySQL 트랜잭션을 외부 서비스 처리 중 계속 유지하지 않을 수 있음.
- **단점:** MySQL 커밋 직후 프로세스가 종료되면 **이벤트 발행이 누락**될 수 있음. 이벤트 처리 실패·중복 수신·모델 호출 재시도도 별도 설계가 필요함.
- **핵심 보완점:** 메모리 이벤트만으로는 자동 복구가 보장되지 않음. 영속적인 전달 상태/작업 기록이 필요함.

### D. MySQL 인덱싱 상태 + Scheduler가 미완료 작업 처리

- **장점:** DB에 남아 있는 미완료 작업을 재시작 후에도 조회하고 복구 가능. 이벤트 브로커 없이 출발할 수 있음.
- **단점:** 실행 주기에 따라 인덱싱 지연 발생, 스캔/동시 실행 제어 필요.
- **주의:** Scheduler도 재시도 횟수·간격·실패 분류·멱등성 설계가 필요함. 반드시 DB 자원을 오래 점유하는 것은 아님.

### E. 이벤트 기반 빠른 반영 + DB 상태/Scheduler 보완

- **장점:** 평상시 빠르게 반영하고 이벤트 누락·실패 시 미완료 작업을 다시 찾을 수 있음.
- **단점:** 처리 경로와 관리 지점이 늘어남. **이벤트 누락을 감지할 영속 기록**이 없다면 보완 효과가 제한적임.

### 추가로 검토할 방식: Transactional Outbox

- MySQL 트랜잭션에서 **원본 변경과 인덱싱 요청 기록(outbox)**을 함께 커밋하고, 별도 처리자가 인덱싱 작업을 전달·실행하는 패턴.
- 전달 누락 방지에 도움을 주지만, **중복 전달은 여전히 가능**하므로 Qdrant Upsert와 처리 상태 갱신의 멱등성 설계가 필요함.
- 이 방식 또는 더 단순한 DB 상태 기반 작업 기록 중 어느 쪽을 채택할지는 상세 설계에서 결정.

## 4. 현재 결정(잠정)

- **MySQL에 원본 데이터를 먼저 커밋**하고, Qdrant 인덱싱은 **별도 비동기 작업**으로 수행한다.
- **대안 C의 비동기 분리 방향을 유지**하지만, 순수 메모리 이벤트만으로 일관성을 보장한다고 주장하지 않는다.
- 인덱싱 작업이 유실되지 않도록 하는 **영속적 기록과 재처리 전략은 미결정**이다(D / E / Outbox 등 검토 예정).
- 원본 상태와 인덱싱 상태를 분리한다. Qdrant는 원본이 아니며, 검색 시 필요한 경우 MySQL의 최신 상태를 확인한다.

## 5. 선택 이유 및 포기하는 것

- 원본 데이터 소유권을 MySQL로 일원화하고, Qdrant 실패를 이유로 원본 데이터를 잃지 않기 위해서.
- 임베딩·Qdrant 호출 시간이 길어져도 MySQL 트랜잭션을 지속적으로 점유하지 않기 위해서.
- **대가:** 즉시 검색에 반영되지 않는 구간(Eventual Consistency)이 생기며, 인덱싱 상태·재처리·중복 방지 로직이 추가됨.
- A는 고아 벡터 발생 위험, B는 운영 자원 증가로 현재 우선순위에서 제외. D/E/Outbox는 C의 신뢰성 보완 대안으로 계속 검토.

## 6. 예상 영향 및 실패 시나리오

|상황|기대되는 동작 / 남은 설계|
|---|---|
|MySQL 커밋 전 실패|원본 변경 미반영; Qdrant 반영 작업을 시작하지 않아야 함|
|MySQL 커밋 직후 프로세스 종료|**반드시 복구 경로 필요**: 작업의 영속적 기록을 통해 누락 발견·재처리|
|임베딩 성공, Qdrant 실패|벡터를 별도 보존하지 않았다면 재시도 시 재임베딩 가능|
|Qdrant 성공, 완료 표시 실패|재시도 시 같은 사례/버전에 대해 안전한 Upsert 필요|
|RESOLVED → OPEN / 삭제|과거 벡터가 검색되지 않도록 제거 또는 필터 반영 필요|
|해결된 사례 수정|구버전 벡터가 현재 사례로 취급되지 않도록 갱신·버전 검증 필요|

- 장점: 원본 보존, 외부 서비스 실행 시간과 DB 커밋의 분리.
- 단점: 최종 일관성, 인덱싱 지연, 실패/중복 복구에 대한 추가 관리 필요.
- RAM 사용량이나 재임베딩 감소는 **현재 설계만으로 보장하지 않으며 측정 필요**.

## 7. 재검토 조건

- MySQL 커밋 이후 이벤트/작업 전달 누락을 재현했을 때 복구할 수 없는 경우.
- 반복 장애로 인덱싱 지연이 허용 범위를 넘거나 검색 결과의 정합성을 확보하지 못하는 경우.
- 동시 인덱싱·모델 교체 시 중복 또는 구버전 벡터가 발생하는 경우.
- 안정적인 재처리를 위해 필요한 구현 복잡도가 MVP 범위를 넘어서는 경우.
