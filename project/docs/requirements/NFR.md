# 1. 비기능 요구사항 (핵심)
## 1.1 성능

- **NFR-01. 검색 성능:** 입력값 임베딩부터 유사 품질사례 조회 및 JEV(또는 Reranker) 평가·필터링 완료까지, 요청의 95% 이상은 **3초 이내**에 처리되어야 한다.
- **NFR-02. AI 분석 성능:** 검색 단계 완료 이후 검색된 품질사례를 활용한 AI 원인 분석·정리 단계는 요청의 95% 이상이 **15초 이내**에 완료되어야 한다.
- **NFR-03. 동시 요청:** 초기 개발 환경에서는 **동시 분석 요청 5건**을 수용하는 것을 목표로 한다. 동시 접수와 동시 실행의 구분 및 측정 조건은 부하 테스트 전에 정의한다.

## 1.2 자원 제약 및 가용성

- **NFR-04. 메모리:** 실행 환경의 **전체 메모리 사용량은 최대 16GB**로 제한한다. 서비스별 메모리 배분은 모델 선정 및 부하 테스트 후 결정한다.
- **NFR-05. 임베딩 서비스 가용성:** Embedding 서비스의 일부 인스턴스에 장애가 발생해도 다른 정상 인스턴스를 통해 처리를 지속할 수 있어야 한다. 단, 16GB 환경에서 실현 가능한지는 검증한다.

## 1.3 보안 및 접근 통제

- **NFR-06. 데이터 보호:** 품질사례 및 관련 데이터가 권한 없는 사용자나 외부에 노출되지 않아야 한다.
- **NFR-07. 사용자 권한:** 사용자의 역할에 따라 품질사례 **등록·수정·조회·해결 처리** 권한을 제한해야 한다. 팀장과 일반 팀원의 구체적인 권한 범위는 별도로 확정한다.
- **NFR-08. 내부 저장소 보호:** MySQL과 Qdrant는 외부에 직접 공개하지 않아야 한다. 서비스 계정의 DB 접근 권한은 사용자 역할 권한과 별도로 관리한다.
- **NFR-09. 외부 접근 제한:** 시스템은 허가되지 않은 외부 접근을 차단해야 한다. (운영 환경의 외부 송신 통신 정책은 별도 결정)
- **NFR-10. 통신 보호:** 사용자와 서버 간 통신에는 HTTPS를 적용하여 전송 중인 데이터를 보호해야 한다.
- **NFR-11. 비밀정보 관리:** DB 비밀번호와 API Key 등 민감한 설정값은 소스코드에 직접 포함하지 않고 안전하게 관리해야 한다.
- **NFR-12. AI 입력 안전성:** 품질사례에 포함된 텍스트가 AI 시스템의 상위 명령으로 취급되지 않도록 방어책을 마련해야 한다. 구체적인 방어 방법은 추가 학습 후 결정한다.

## 1.4 데이터 일관성 및 신뢰성

- **NFR-13. 원본 데이터 보존:** MySQL과 Qdrant 간 데이터 불일치가 발생하더라도 원본 품질사례 데이터는 보존되어야 한다.
- **NFR-14. 불일치 복구:** MySQL과 Qdrant 간 데이터 불일치를 탐지하고 복구할 수 있어야 한다.
- **NFR-15. 분석 작업 상태:** 비동기 분석 작업은 대기·진행·완료·실패 등의 상태를 확인할 수 있어야 하며, 실패한 작업은 필요한 경우 재처리할 수 있어야 한다.
- **NFR-16. 자동 재처리:** **재시도 가능한 일시적 장애**로 분석이 실패한 경우 정해진 재시도 정책에 따라 자동으로 재처리할 수 있어야 한다.
- **NFR-17. 중복 처리 방지:** 동일한 분석 작업의 중복 요청이나 재시도가 발생해도 결과가 중복 생성되거나 데이터 일관성이 훼손되지 않아야 한다. 단, 동일 품질사례에 대한 새로운 분석 작업은 허용할 수 있어야 한다.
- **NFR-18. 데이터 영속성:** 서비스 또는 컨테이너가 재시작되어도 저장된 품질사례와 분석 결과는 유지되어야 한다.

## 1.5 AI 결과 신뢰성

- **NFR-19. 결과 검증:** AI 분석 결과는 정의된 데이터 형식과 참조 근거의 유효성을 검증해야 하며, 형식 검증에 실패한 결과를 정상 완료 결과로 저장해서는 안 된다.
- **NFR-20. 근거 추적:** AI가 제시한 원인 후보는 참조한 품질사례와 연결하여 근거를 확인할 수 있어야 한다.
- **NFR-21. 최종 판단 분리:** AI 분석 결과와 담당자의 최종 판단은 구분하여 관리되어야 한다.

## 1.6 유지보수성 및 관측 가능성

- **NFR-22. 모델 교체 용이성:** Embedding 및 LLM 모델을 교체할 때 주요 비즈니스 로직의 수정을 최소화할 수 있어야 한다.
- **NFR-23. 요청 추적:** 하나의 분석 작업이 여러 서비스를 거쳐도 요청 ID 및 분석 작업 ID를 통해 처리 과정과 오류를 추적할 수 있어야 한다.

## 2. 추후 도전 목표 (초기 필수 범위에서 제외)

- **모델 무중단 교체:** Embedding 및 LLM 모델을 서비스 중단 없이 전환하는 것을 목표로 한다.
- 모델 전환 시 **신규 요청은 새 모델**에서 처리하고, 이전 모델에서 실행 중인 작업은 종료 정책에 따라 마무리한다. 기존 문서의 '**1분 이상 대기 후 종료**'는 검증되지 않은 가정이므로 고정 정책으로 확정하지 않는다.
- 임베딩 모델 교체 시 기존 벡터의 재임베딩 및 Qdrant 컬렉션 전환 가능성을 검토한다.

## 3. 미정 사항 / 추가 학습 필요

- **성능 측정:** 단일 요청/동시 5건 부하에서 3초·15초 목표를 어떻게 측정할지; 로컬 LLM 및 Embedding 모델이 16GB 제약을 만족하는지.
- **역할별 권한:** 팀장과 일반 팀원이 실제로 수행할 수 있는 등록·수정·조회·해결 처리의 범위.
- **비밀정보 관리:** 개발·배포 환경별 DB 비밀번호, API Key 보관·주입·접근 권한 방식.
- **프롬프트 인젝션:** 구체적인 예방·검증 정책. 입력 추적 기록은 방어책을 대신하지 않으며 민감정보 보관 범위도 결정해야 함.
- **비동기 작업 처리:** 작업 큐, 타임아웃, 재시도 횟수·간격, 중복 요청 식별 방식 및 서버 재시작 후 복구 정책.
- **데이터 일관성:** MySQL을 원본 데이터의 기준으로 삼을지, Qdrant 저장 실패·수정·삭제 시 동기화 및 보상 처리 방법.
- **네트워크:** '외부 접근 차단'과 '외부로 나가는 통신 차단'의 적용 범위.
- **확장·가용성:** Embedding 다중 인스턴스와 동시 분석 5건이 현재 장비에서 가능한지; 불가능한 경우 초기 범위 조정.
