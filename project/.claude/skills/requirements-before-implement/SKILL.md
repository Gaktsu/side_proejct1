# 구현 전 요구사항 정리

설계는 여러 갈래(설계 확정안, Q&A 문서, CLAUDE.md, 그리고 아직 문서에 안 들어간 대화)에 흩어져 결정된다. 구현 중에 이걸 매번 다시 모으면 대화 중간에 바뀐 결정(예: "upsert 전에 deleted_at 확인" → "확인하지 않음")을 옛 버전으로 구현하기 쉽다. 그래서 구현 전에 **최종 결정만** 한 파일에 모아 사용자가 확인하고, 구현이 끝나면 같은 파일을 체크리스트로 써서 빠진 것이 없는지 검증한다. 순서도(`verification/diagrams/`)와 함께 사용자의 검증 보조 자료다.

## 1. 모으기

다음 출처를 읽고, 서로 다르면 **나중에 정한 것**을 따른다.

1. 이번 대화 — 사용자가 확정한 말, 정정한 말 ("그렇게 가자", "그건 빼", "A안으로")
2. 해당 설계 폴더의 확정안·Q&A (경로는 CLAUDE.md에 있음, 예: `설계/LLD 정합화/LLD4 기반 설계 구체화/`)
3. `CLAUDE.md`의 확정 사항·도메인 규칙, 저장소 `docs/`(LLD)

대화에서 뒤집힌 결정은 최종 값만 적고, 뒤집혔다는 사실이 구현에 영향이 있으면(같은 실수를 반복하기 쉬우면) "주의"에 한 줄로 남긴다.

## 2. 파일 쓰기

위치: `verification/requirements/<주제>.md` (예: `lld4-reopen-delete-restore.md`). 같은 주제 파일이 이미 있으면 새로 만들지 말고 고친다.

아래 형식을 쓴다. 해당 없는 섹션은 지운다. 각 항목은 **구현 후 참/거짓을 판정할 수 있는 문장**으로 쓴다 — "삭제를 잘 처리한다"가 아니라 "삭제된 사례는 restore 외 모든 API에서 404". 그래야 3단계에서 체크리스트로 쓸 수 있다.

```markdown
# <주제> 요구사항

- 상태: 구현 전 | 구현됨 (YYYY-MM-DD, 브랜치 <이름>)
- 출처: <설계 문서 경로>, 대화 (YYYY-MM-DD)

## 범위
- 이번에 만드는 것 / 이번에 만들지 않는 것 (명시적으로 뒤로 미룬 것 포함)

## API
| ID | Method | 경로 | 성공 | 실패 |
|---|---|---|---|---|
| A1 | POST | /api/... | 200 ... | 404 ... / 409 ... |

## 도메인 규칙
- [ ] R1. ...

## 데이터·스키마
- [ ] D1. Flyway V<n>: ...

## 비동기·동시성
- [ ] C1. ... (어느 스레드가 어느 값을 쓰는지 처음부터 명시)

## 미정·나중에
- ... (지금 구현하지 않고 남긴 판단, 측정 후 결정할 것)

## 주의
- ... (대화에서 뒤집힌 결정 중 헷갈리기 쉬운 것)
```

ID(A1, R1, D1, C1)를 붙이는 이유: 사용자가 "R3 다시 보자"처럼 짚을 수 있고, 테스트·순서도와 연결할 때 쓴다.

## 3. 확인받기

파일을 쓴 뒤 사용자에게 경로와 항목 수를 알리고, **확인을 받기 전에는 코드를 쓰지 않는다**. 이 사용자는 구현 전에 구상을 승인받는 방식을 원한다. 대화에서 결정이 애매했던 항목(두 해석이 가능한 것)은 따로 짚어 묻는다. 수정 요청이 오면 파일을 고치고 다시 확인받는다.

확인되면 domain-api-feature 스킬로 구현을 진행한다.

## 4. 구현 후 점검

구현과 테스트가 끝나면 이 파일로 돌아와:

- 각 항목의 `[ ]`를 `[x]`로 바꾸고, 뒤에 근거를 붙인다: 테스트 메서드 이름 또는 순서도 파일 (`— QualityCaseControllerTest.삭제된_사례_조회시_404`, `— verification/diagrams/05-quality-case-delete.md`).
- 근거가 없는 항목은 체크하지 않고 보고에 "테스트 없음 / 수동 검증 필요"로 적는다.
- 구현 중 요구사항이 바뀌었으면(사용자와 합의한 경우만) 항목을 고치고 "주의"에 바뀐 이유를 남긴다. 설계 확정안 문서도 같이 고친다.
- 맨 위 상태를 "구현됨"으로 바꾼다.

커밋은 사용자가 요청할 때만 한다.
